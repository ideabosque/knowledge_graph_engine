## 2. Purpose and Scope

Validate that the knowledge_graph_engine dual-backend implementation works correctly with `db_backend=postgresql`, and that the full extraction → search → RAG workflow operates against a real Neo4j instance when the **source text is derived from the flight-product dataset** generated by the RFQ Engine. This certifies (a) the repository dispatch boundary and 5 PostgreSQL repositories, (b) single-active invariants, (c) GraphQL dispatch, and (d) the cross-system data flow PG metadata → Neo4j graph (flight entities) → search results → PG request record.

- **In scope:**
  - PostgreSQL connection initialization (`Config._initialize_db_session`)
  - Table creation via `Base.metadata.create_all` (5 KGE tables) — **within the shared `silvaengine` database, with a documented collision risk on the `requests` table**
  - All 5 entity repositories: CRUD operations through `get_repo()`
  - Single-active invariant for `graph_schema` and `neo4j_instance` (application + partial unique index)
  - GraphQL query/mutation execution through `dispatch_graphql` with PG backend
  - DataLoader dispatch (`PGRequestLoaders`)
  - Cache config backend-awareness
  - **Neo4j instance registration** (real `bolt://localhost:7687`, user `neo4j`, db `neo4j`)
  - **GraphRAGUtil initialization** with active Neo4j instance from PG repo
  - **Flight product data ingestion**: `flight_products.json` is serialized into descriptive text passages (one per item / route / bundle) and fed to `executeExtract`
  - **Knowledge graph extraction** — flight entities (Airline, Airport, Route, CabinClass, Flight, Bundle) and relationships written to Neo4j
  - **Vector search** (`search` query with `search_mode=vector`) against Neo4j using flight-themed queries (e.g. "Which airlines fly from SFO?")
  - **RAG query** (`rag` query) answering flight questions from Neo4j context
  - **Request recording** — search/rag results persisted to PG `requests` table (**blocked by table collision — see §8 risk R-001**)
  - **Schema resolution** — active schema loaded from PG, used by extraction
  - **Cross-system data flow**: PG metadata → Neo4j flight graph → search results → PG request record

- **Out of scope (assumed unavailable — deferred to future certification):**
  - DynamoDB backend live tests
  - silvaengine_gateway HTTP integration
  - WooCommerce extraction
  - Schema evolution via LLM (covered by existing `test_schema_evolution_live.py`)
  - Re-running `prepare_flight_products.py` itself (the JSON fixture already exists and is treated as the source of truth)

- **System(s) under test:** `knowledge_graph_engine` module with `DB_BACKEND=postgresql` + Neo4j 5.x (`bolt://localhost:7687`, db `neo4j`) + OpenAI gpt-4o

## 6. Execution Order

```text
Foundation (Config + PG) → Table introspection → Neo4j Instance CRUD →
Graph Schema CRUD (single-active) → Document CRUD → Request CRUD (blocked, R-001) →
DocProcessError CRUD → GraphQL dispatch → DataLoader → PartialIndex → CacheConfig →
Neo4j Registration (flight-neo4j) → Flight Schema Registration →
Flight Data Extraction (5 passages) → Vector Search (flight queries) →
RAG (flight queries) → Neo4j node reconciliation → Cleanup
```

**Reason:** Neo4j instances and graph schemas are referenced by extraction. Flight passages depend on an active schema + active Neo4j instance. Search/RAG depend on extraction having populated Neo4j.

## Appendix A — Known Risk R-001: `requests` Table Collision

The user-selected `silvaengine` database contains a `requests` table created by `rfq_engine` with columns `email`, `request_title` (NOT NULL), `request_description`, `billing_address`, etc. KGE's `RequestModel` (`models/postgresql/request.py`) defines the same table name with incompatible columns (`user_query`, `cypher_query`, `search_mode`, `results` JSONB). Consequences:

- `Base.metadata.create_all` will **not** recreate the existing table (SQLAlchemy skips existing tables).
- KGE request inserts (search/RAG result recording) will fail with `NotNullViolation` on `email`/`request_title`.
- Scenarios INT-005 and the request-recording validation points of INT-014/INT-015 are **blocked**, not failed.

**Mitigation options (not applied without user approval):**
1. Use a dedicated KGE database (e.g. `kge_flight`) — recommended, but user chose `silvaengine`.
2. Create a separate PostgreSQL schema (`kge` schema) and set `search_path`.
3. Rename KGE's table to `kge_requests` (code change, out of scope).

This risk is recorded as a **certification condition** if all other scenarios pass.
